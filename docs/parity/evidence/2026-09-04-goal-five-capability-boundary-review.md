# Goal Five Phase 1 Capability And Boundary Review

Date: 2026-09-04

Program item: `P1-02`

Implementation baseline: `e1d78a1ef256bf91caf01b510d0ca856eafdd27a`
Machine catalog:
[`artifacts/2026-09-04-goal-five-capability-catalog.json`](./artifacts/2026-09-04-goal-five-capability-catalog.json)

## Decision

VizEngine has a coherent production-capable core rather than a collection of
isolated demos. The portable project, session, action, runtime, capability-pack,
renderer, editor-control, and UI-projection boundaries are real and already
support an ambitious treatment. Phase 1 should therefore compose the flagship
from the existing palette first and add capabilities only where the treatment
demonstrates a reusable gap.

The largest current mismatch is not missing visual components or an inability
to obtain autonomous full-fidelity proof. The existing repository
`render:browser-bundle` harness already opens a portable bundle in headless
Studio, invokes its full-fidelity render service, downloads the result, and
reports visual/performance feedback. The mismatch is that the standalone
product CLI does not compose or render the same capability surface: local
`bundle render-job` uses core registries and the structural SVG executor, while
Studio composes full Three rendering plus the trusted Signal Cathedral
extension. Canonical standalone host composition is therefore the leading
product gap; building another proof harness would be duplication. This review
records the gap without prematurely choosing its implementation.

## Audited Observation

The catalog is generated by interrogating executable registries only when the
tracked implementation source exactly matches the pinned baseline. Every
package, component, node, Three program, project, tool, and parity source
reference is then bound to its Git object identity. The complete immutable JSON
is also bound to one expected SHA-256 digest, so later validation rejects
semantic tampering without pretending that changed future code is still the
audited tree.

This rejects several plausible false passes:

- registration alone does not imply authorability, execution identity,
  renderer reach, host composition, or exercised use;
- an editor-visible capability is not assumed to exist in local headless
  composition, and the inverse is not assumed either;
- CLI usage declarations and executable dispatch actions are compared as sets;
  help is generated from that same registry rather than treated as independent
  evidence;
- VizControl's broad in-process interface is not conflated with its 24 exposed
  wire operations;
- use in one production does not automatically promote a production-local
  capability into reusable core;
- shader source files are implementation details of their owning components or
  programs, not ten additional portable capabilities;
- a successful structural SVG render does not prove shader or Three visual
  fidelity.

The validator is intentionally a narrow P1-02 audit, not a generic capability
intelligence framework.

### Components

The curated core palette is:

- Curve Spectrum, Debug Animation, Feature Extraction Bars, Fullscreen Shader,
  Heartbeat Monitor, Instanced Supercube, Light Tunnel, Morph Shapes, Neural
  Network, Noise Shader, Orbiting Cubes, Particle System, Simple Cube, Stage
  Scene, and Strobe Light.

The five runtime-only primitives are `solid-color`, `cover-image`,
`reactive-bars`, `radial-bloom`, and `feature-channel-bars`. All five lack both
an authoring schema and an implementation version. They must not be described
as catalog-ready or execution-manifest-ready. Gate 1 may decide that some are
deliberately internal; promotion should happen only when the treatment needs a
real authoring surface.

Signal Cathedral contributes exactly one trusted production-local component
and one Three program through the Studio's single capability-composition root.
Afterlight Assembly contributes no pack: it is a composition-only production
over the reusable Stage Scene capability. These are deliberately different
reuse classifications.

The eight core Three programs cover simple and instanced geometry, particles,
orbiting geometry, a light tunnel, morphing shapes, a neural network, and the
full animated Stage Scene. The Stage Scene retains the existing model and
animation pipeline; this audit does not recommend replacing authored character
assets with lower-fidelity procedural substitutes.

### Graphs, actions, and control

The 34-node registry already spans arithmetic, shaping, oscillation, MIDI,
audio features, rhythm, color, selection, temporal integration/decay, and graph
input/output responsibilities. `decay` and the special `Output` node are the two
entries without the common editor-authoring metadata. This is an explicit
classification, not automatically a defect.

The 22 durable actions cover assets, artifacts, layers, timeline, graph
lifecycle, graph inputs, nodes, positions, bindings, outputs, and enablement.
They remain the canonical persistent mutation language. Continuous editor
gestures and transient preview controls do not need to become project actions.

The 24 wire operations cover discovery, snapshots, project/bundle access,
component/node/graph/runtime/frame/render/debug inspection, atomic
transactions, history, transport, jobs, baking, render start, downloads, and
cancellation. Host-only transient VizControl methods remain in-process
attachments rather than an accidentally enlarged remote protocol.

### Inspection and feedback tools

Seventeen current repository commands are explicitly inventoried with their
implementation, observation, and honest limitation:

- canonical creative-loop smoke and full-fidelity browser-bundle rendering;
- runtime-preview and Light Tunnel runtime benchmarks;
- headed Light Tunnel, editor interaction, Signal Cathedral node-editor,
  endurance, workspace-resize, audio, and waveform/Rhythm Lab benchmarks;
- audio-artifact container measurement and identity-compatible runtime
  performance comparison;
- parity, Goal Five criterion, source-metric, and broad browser-journey checks.

Together with the product CLI's frame, render, graph-runtime, and debug
inspection operations, this is a strong existing sensory surface. Its gaps are
specific: runtime-only benchmarks omit browser/GPU cost, workload benchmarks
are intentionally fixed, structural proofs omit advanced visual content, and
automated browser checks do not replace aesthetic judgment. The treatment
should reuse these observations and add a new sensor only for a named false pass
they cannot reject.

## Canonical Ownership

| Meaning                            | Canonical owner                       | Forbidden duplicate                                               |
| ---------------------------------- | ------------------------------------- | ----------------------------------------------------------------- |
| Portable project truth             | `@viz-engine/contracts`               | UI, production pack, renderer, or adapter schema forks            |
| Mutable editor truth               | `@viz-engine/editor-session`          | React stores owning a second project/runtime model                |
| Durable mutations                  | `@viz-engine/actions`                 | Agent-only or editor-only mutation semantics                      |
| Graph and frame meaning            | `@viz-engine/runtime`                 | Render-adapter or preview-only evaluation rules                   |
| Executable capabilities            | capability packs and registries       | UI catalogs or loose shader files acting as registries            |
| Full-fidelity browser presentation | Three compositor and program registry | Layer cards, mirrors, or Remotion owning alternate render meaning |
| Human editor projection            | Studio                                | React updates becoming the signal/pointer bus                     |
| Product control                    | VizControl and `pnpm viz`             | Maintainer `pnpm repo` duplicating product semantics              |

The Studio and local CLI currently have intentionally visible composition
differences, but they must not acquire different project or runtime semantics.
The correct future repair is a canonical host/capability composition and render
attachment that headless workflows can select explicitly, not a second local
engine.

## Treatment-Prioritized Gaps

1. **Standalone full-fidelity host composition.** Local `bundle render-job`
   cannot prove shader, Three, or production-local content. The repository
   browser-bundle harness already provides autonomous Studio-path proof, so the
   remaining gap is a canonical reusable host/capability composition and
   product render attachment—not another sensory workaround. The treatment
   should define the exact standalone consumer before architecture is changed.
2. **Macro direction and cues.** There is no durable act/cue/direction contract
   above raw timelines and graphs. The treatment must first prove the vocabulary
   worth making canonical.
3. **Compositor modulation.** Layer opacity, blend mode, and transform remain
   static project properties. Add graph-driven ownership only for named
   treatment transitions or whole-frame modulation.
4. **Runtime-only primitive disposition.** Decide whether each of the five
   hidden core primitives remains internal or gains a versioned authoring
   contract. Do not expose them mechanically.
5. **Multi-graph usage and cost inspection.** Runtime inspection reports values
   and issues, but not canonical responsibility/usage/cost attribution per
   graph. Build only the observation demanded by the flagship's real graph
   organization.
6. **Conditional media and generic model authoring.** There is no generic
   catalog Model3D component, Cover Image is runtime-only, and the authorized
   input audit found no new standalone image/video source. Add these only if
   Stage Scene, the four authorized Stage models, shaders, and procedural
   capabilities cannot express the approved treatment.

The ordering reflects likely treatment value, not implementation permission.
P1-03 and the Gate 1 treatment can reorder or eliminate items using music and
creative evidence.

## Explicit Non-Goals For This Phase

- no universal untrusted model or plugin ingestion;
- no facial, speech, singing, or root-motion framework;
- no generic subgraph, template, mask, or effect-graph system without a named
  treatment criterion;
- no promotion of Signal Cathedral behavior merely because it already works in
  Studio;
- no renderer workaround that creates a second runtime meaning;
- no speculative sensor framework detached from a false pass the flagship can
  actually encounter.

## Assumptions And Human Boundary

- Implementation at the pinned revision is source of truth. Documentation is
  used to interpret intent but cannot invent a capability.
- Registration, authorability, execution identity, renderer reach, host reach,
  and exercised consumers are separate evidence dimensions.
- Production-local behavior earns core promotion only through a second real
  consumer or a stable domain boundary.
- V1 parity remains a floor; the flagship should preserve the existing smooth,
  responsive, intuitive, fully featured editor while extending capability.
- Structural SVG is valid diagnostic evidence but never visual-fidelity proof
  for omitted node kinds.

Humans still own treatment value, aesthetic and emotional judgment, whether a
hidden primitive should become public, whether production-local behavior has
earned promotion, and final rendered-result approval. The next machine-owned
step is `P1-03`: compare candidate music windows with deterministic audio
evidence. The next human gate remains the treatment decision after that audit;
this checkpoint does not resolve it.
